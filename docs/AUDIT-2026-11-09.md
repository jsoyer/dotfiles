# Audit du dépôt — 9 novembre 2026

Base examinée : `8ba3304a`, avec la suppression locale des déclarations VS Code dans `Brewfile_personal` déjà présente avant l'audit.

## Périmètre et méthode

Revue ciblée des chemins exécutables : scripts chezmoi, mises à jour automatiques, wrappers de paquets, orchestration fleet, gestion des secrets, CI et gestion des fichiers dans aictx. Le dépôt contient 4 224 fichiers suivis, dont 103 templates, 188 fichiers Python et 27 fichiers Rust. Ce document ne constitue pas une revue ligne à ligne de tous les contenus vendus sous `dot_aictx` et `dot_claude`, ni un audit des dépendances externes ou de l'historique Git à la recherche de secrets.

Les reproductions shell utilisent des répertoires temporaires et des commandes simulées ; aucun paquet ni configuration réelle de machine n'a été modifié. Les observations Rust ci-dessous sont issues de la lecture du code ; elles n'ont pas été exécutées dans un binaire recompilé. Aucun correctif de production n'est inclus dans cet audit.

P1 : risque de perte de configuration à traiter en premier. P2 : fiabilité, conservation des données ou lacune de validation à traiter ensuite.

## Constats prioritaires

### A01 — P1 — Le générateur SSH écrase la configuration Linux

**Source :** [run_onchange_generate-ssh-config.sh.tmpl:12](../.chezmoiscripts/03-configure/run_onchange_generate-ssh-config.sh.tmpl#L12).

La branche Linux utilise `>` sur `~/.ssh/config` et ne réécrit que deux lignes, dont `IgnoreUnknown UseKeychain`. Aucun bloc `Host` existant n'est conservé. Au premier passage ou lorsque le script change, les alias, utilisateurs et paramètres de connexion existants disparaissent. Le risque est particulièrement gênant pour les machines auxquelles on accède via ces alias.

**Reproduction :** un fichier temporaire contenant `Host example` perd ce bloc après exécution de la branche Linux ; le script sort en 0.

**Correction proposée :** définir explicitement la propriété de ce fichier. Préférer un fragment dédié dans `~/.ssh/config.d/` et un `Include` ajouté sans écraser le contenu existant. Si le fichier doit être intégralement généré, prévoir sauvegarde, génération complète et remplacement atomique. Ajouter un test préservant un hôte préexistant.

### A02 — P1 — Une panne partielle de 1Password détruit le dernier fichier de secrets valide

**Source :** [run_onchange_generate-secrets.sh.tmpl:65](../.chezmoiscripts/03-configure/run_onchange_generate-secrets.sh.tmpl#L65), écriture à la ligne 90.

Après les contrôles initiaux, chaque `op read` en échec est converti en chaîne vide. Le fichier existant est ensuite tronqué avant que les nouvelles valeurs soient ajoutées. Une session 1Password perdue ou une panne entre les contrôles et les lectures remplace donc un fichier valide par un fichier partiel ou sans secrets, avec un code de succès. La génération Bash recopie ce résultat.

**Reproduction :** `op account list`, `whoami` et `item get` réussissent, puis les lectures de champs échouent : code 0, ancienne valeur supprimée, zéro export restant.

**Correction proposée :** lire l'item en une opération, distinguer champ facultatif absent et erreur de lecture, générer dans un fichier temporaire en mode 0600 situé dans le répertoire cible, valider puis renommer. Conserver les versions Zsh et Bash précédentes en cas d'erreur. Tester aussi une interruption d'écriture. `umask 077` seul ne resserre pas les permissions d'un fichier déjà existant ; la création du temporaire doit garantir ce mode dès le départ.

### A03 — P1 — `aictx reset` supprime les réglages personnels

**Source :** [symlinker.rs:293](../tools/aictx/src/symlinker.rs#L293).

`reset` supprime intégralement `settings.local.json` pour chaque CLI applicable, sans vérifier si aictx l'a créé ni préserver les clés personnelles. Pourtant `apply` fusionne ses réglages dans un JSON existant. Un utilisateur qui avait déjà des permissions ou d'autres réglages locaux les perd donc lors du reset. Le traitement de `settings.json` en scope UserProject est plus sélectif, ce qui montre une incohérence de politique de conservation.

**Validation :** constat direct dans le code ; tests Rust non exécutés, voir limites.

**Correction proposée :** suivre les clés et entrées réellement ajoutées par aictx et ne retirer qu'elles ; conserver les autres valeurs et ne supprimer le fichier que s'il devient vide. Ajouter un test avec des réglages utilisateur présents avant un cycle apply/reset.

### A04 — P2 — Les échecs de `brew bundle` deviennent des succès définitifs pour chezmoi

**Source :** [run_onchange_03-brew-bundle.sh.tmpl:52](../.chezmoiscripts/02-install/run_onchange_03-brew-bundle.sh.tmpl#L52).

Les deux passes des deux helpers finissent par `|| true`. Même si toutes les installations échouent, la fonction renvoie 0. Le script `run_onchange` peut alors être enregistré comme exécuté : un simple nouvel apply ne relancera pas nécessairement les dépendances manquantes tant que son contenu rendu ne change pas. Cela explique pourquoi un message de poursuite du déploiement peut coexister avec une installation incomplète.

**Reproduction :** commande `brew` simulée retournant 42 aux deux passes ; le helper retourne 0.

**Correction proposée :** continuer les étapes indépendantes, mais agréger les échecs et retourner un code non nul à la fin, ou mettre en place une réconciliation idempotente avec état explicite et nouvelle tentative. Éviter un simple `set -e` global qui empêcherait les étapes indépendantes de se terminer. Le même problème de report sans nouvelle tentative est explicitement documenté dans [l'installateur fleet:19](../.chezmoiscripts/03-configure/run_onchange_install-fleet-agent.sh.tmpl#L19) ; traiter également ce cas sans demander de purger tout `scriptState`.

### A05 — P2 — `sysup` annonce un succès malgré les échecs des mises à jour macOS

**Source :** [executable_sysup:251](../dot_local/bin/executable_sysup#L251), sortie à la ligne 364.

La branche macOS appelle `breww upgrade`, `breww cu -a` et `mas upgrade` sans accumuler leurs codes d'erreur. Le script sort avec `_sysup_rc`, initialisé à zéro et modifié dans certaines branches Linux seulement. Un appelant utilisant le statut de sortie reçoit donc un faux succès sur Mac.

**Reproduction :** Homebrew, breww et mas simulés en échec avec code 42 ; sortie finale du script en 0.

**Correction proposée :** définir les étapes obligatoires par plateforme, agréger leurs erreurs, laisser les compléments facultatifs poursuivre puis retourner un statut fidèle. Ajouter un test macOS simulé et vérifier que le statut se propage aux appelants.

### A06 — P2 — Un JSON illisible est remplacé silencieusement dans aictx

**Source :** [symlinker.rs:557](../tools/aictx/src/symlinker.rs#L557), même politique dans `remove_cctx_keys_from_settings`.

`serde_json::from_str(...).unwrap_or_default()` transforme une erreur de lecture du format en objet vide. Lors d'un apply ajoutant des sélections MCP ou plugins, un fichier JSON momentanément tronqué ou contenant une erreur de syntaxe est ainsi remplacé par les seules clés aictx, ce qui détruit le contenu initial. Lors du nettoyage, un objet devenu vide peut conduire à la suppression du fichier.

**Validation :** lecture du code, sans exécution Rust.

**Correction proposée :** remonter l'erreur de parsing avec le chemin du fichier, préserver les octets existants et proposer une réparation explicite. Utiliser un temporaire unique pour les écritures, plutôt qu'un nom `.json.tmp` partagé entre exécutions concurrentes. Tester les fichiers invalides, les clés personnelles et deux exécutions concurrentes.

### A07 — P2 — La CI ne lance pas la majorité des tests Python et ne valide pas réellement macOS

**Source :** [.github/workflows/validate.yml:18](../.github/workflows/validate.yml#L18), sélections de tests à partir de la ligne 42 et rendu à partir de la ligne 231.

Le workflow lance trois fichiers Python de garde et les tests Rust, mais pas les suites fleet, wrappers Homebrew, OS checks ou média. Les régressions dans ces ensembles peuvent donc passer malgré une CI verte. Changer seulement `machine_profile` en `mac-pro` sur Ubuntu ne change pas `.chezmoi.os` : les branches `darwin` restent inactives. ShellCheck examine principalement les fichiers shell non templatisés et certains templates de `dot_local/bin`, tandis que les scripts chezmoi rendus reçoivent surtout une vérification syntaxique.

**Correction proposée :** ajouter un point d'entrée de tests reproductible, exécuter les suites stdlib Python dans la CI et ajouter une matrice Ubuntu/macOS, puis Windows pour les scripts PowerShell. Tester les profils au rendu avec des données et prérequis explicites. Inclure les scripts chezmoi rendus dans ShellCheck. Ajouter `--locked` aux builds Rust de CI et de release pour faire respecter le lockfile suivi.

### A08 — P2 — La suite média n'est pas lançable directement depuis les sources

**Source :** [bin/test_media_automation.py:22](../bin/test_media_automation.py#L22).

Les imports supposent les noms après déploiement, par exemple `media_automation.py`, alors que le dépôt contient `executable_media_automation.py`. Le répertoire de configuration `bin/media_automation/` est chargé à la place comme package namespace ; les fonctions attendues n'existent pas. Les imports des modules auxiliaires et certains chemins explicites ont le même problème.

**Reproduction :** découverte unittest depuis `bin` : 183 tests exécutés, 213 erreurs en comptant les sous-tests. Après copie temporaire des fichiers sous leurs noms déployés, les 212 tests passent. Les différences de compte viennent aussi des classes dont `setUpClass` échoue avant la collecte effective de leurs tests.

**Correction proposée :** adopter le chargement explicite déjà utilisé dans `test_breww.py`, ou fournir un runner qui prépare une arborescence déployée temporaire avant les tests. Documenter une commande qui fonctionne depuis un checkout neuf et l'utiliser en CI.

## Améliorations complémentaires

1. **Limiter l'auto-commit aux overlays générés.** Dans [chezmoi-autoupdate:147](../dot_local/bin/executable_chezmoi-autoupdate#L147), la règle accepte tous les chemins commençant par `dot_private/Brewfile`, `Aptfile`, etc., y compris les bases éditées à la main, puis fait `git add -A` et push. Restreindre la liste aux fichiers réellement possédés par les wrappers et ajouter seulement ces chemins ; une modification manuelle du Brewfile personnel ne devrait pas être publiée comme simple dump automatique sans politique explicite.
2. **Rendre les statuts fiables et structurés.** Centraliser les états succès/partiel/échec et sérialiser les rapports JSON avec une bibliothèque. L'autoupdater échappe actuellement seulement les guillemets de ses erreurs : les retours à la ligne et antislashs ne sont pas correctement pris en charge. Écrire également `status.json` de manière atomique.
3. **Réduire la duplication des wrappers.** `aptw`, `dnfw`, `pacmanw`, etc. réimplémentent validation, choix du manifeste, delta et synchronisation. Extraire progressivement ces fonctions, après des tests de comportement, sans fusionner artificiellement les différences des gestionnaires.
4. **Consolider la détection des plateformes.** Les profils existent dans les templates, le bootstrap et les scripts détachés. Mettre leurs contrats sous tests communs, notamment macOS Intel/ARM, Fedora Atomic et toolbox.
5. **Renforcer la vérification des secrets du dépôt.** Le grep CI ne couvre que quelques extensions de fichiers et formats de jetons ; les scripts sans extension et les fichiers Python sont notamment hors de cette sélection. Utiliser un scanner dédié avec exceptions revues et analyse des nouveaux commits. Aucun secret réel exposé n'a été établi par cet audit.
6. **Documenter la propriété et la réparation des fichiers.** Pour SSH, secrets, réglages aictx et manifests : indiquer qui génère, qui peut éditer, quand la mise à jour est retentée et comment récupérer la dernière version valide. Corriger en particulier les indications « apply pour régénérer » quand le mécanisme réel est `run_onchange` sans changement d'empreinte.

## Ordre de traitement proposé

1. **Conservation des données :** A01, A02, A03 et A06, avec tests de non-écrasement et sauvegarde des fichiers concernés.
2. **Fiabilité des mises à jour :** A04 et A05, avec propagation des erreurs et nouvelles tentatives ciblées.
3. **Validation continue :** A07 et A08, pour rendre les régressions précédentes visibles sur chaque PR.
4. **Maintenance :** propriété des manifests, statuts, duplication et documentation, par petits changements indépendants.

Les protections existantes à conserver incluent la commande SSH imposée de fleet, sa liste blanche de verbes, la validation des inventaires et réponses, les tests de refus, la validation sudoers avant installation et le filtrage des formules Homebrew sans bouteille. La priorité est de fiabiliser la conservation des fichiers et les signaux d'échec autour de ces mécanismes.

## Suivi des corrections locales — 9 novembre 2026

La politique des mises à jour Homebrew a été corrigée après cet audit : `breww` tente désormais la compilation de toutes les formules obsolètes sans bottle utilisable, puis vérifie les paquets restants. Les paquets épinglés ou différés pour des droits administrateur ne sont plus comptés comme une mise à jour complète. Le script de mise à jour Homebrew de chezmoi utilise cette même logique et remonte ses échecs.

A05 est corrigé localement : `sysup` propage maintenant les échecs Homebrew, App Store et mise ; mise est mis à jour avant Homebrew sur macOS. Les autres constats restent à traiter, notamment A04 sur le script d'installation `brew bundle` (distinct du script de mise à jour).

Validation de ce lot : 84 tests Homebrew, 6 tests de propagation des erreurs, 30 tests mise et 93 tests de l'agent fleet passent, soit **213 tests ciblés**. Ruff, la syntaxe Bash de sysup et `git diff --check` passent également. Pas de validation native sur Mac ni de déploiement sur les machines ; les tests d'upgrade utilisent des commandes simulées.
